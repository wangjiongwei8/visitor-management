# Visitor Management System (Open Source) — Operations Manual

> Audience: end users of the system (visitors, host employees, guards, admins).
> The system supports the full flow "visitor scans a fixed QR code to self-register → host reviews → guard checks in and issues badge", with zero external dependencies.

## 1. System Overview & Roles

The Visitor Management System (Open Source) is used for enterprise visitor access management and supports two registration modes (see "1.1 Two Registration Modes").

Core flow centered on **Mode 2 (scan registration)**:
1. The **visitor** scans a fixed QR code at the guard post and fills the appointment form on their phone (no login).
2. After submission, the outcome depends on the **review toggle**:
   - Toggle **off**: auto-approve (status `scheduled`).
   - Toggle **on**: enters pending review (`pending`), reviewed (approved or rejected) by the **host (employee) in person**.
3. The **guard** searches and checks in / out when the visitor arrives; the system auto-issues the matching badge color and auto-intercepts the blacklist.

> **Mode 1 (Pre-registration)**: an employee fills the appointment on behalf of the visitor in the internal backend (a pre-registration form); on submission it auto-passes (`scheduled`). The guard can check in directly on arrival without the visitor scanning. Both modes share the same guard check-in flow.

| Role | Login entry | Main responsibilities |
|------|----------|----------|
| Visitor | Scan to enter, no login needed | Fill appointment |
| Host (Employee) | Backend login | Review visitor scan appointments; can also create pre-registrations |
| Guard | Backend login | Check-in / check-out, badge issuance |
| Admin | Backend login | All system configuration and data management |

> Login URL: `/login` (for Docker deploy typically `http://<server>:4000/login`). The visitor appointment page is `/public/appointment`, pointed to by the fixed QR code.

## 1.1 Two Registration Modes

The system supports two parallel registration / review modes; an organization may use either or both:

- **Mode 1 · Internal backend review (Pre-registration mode)**: an employee fills the visit appointment on behalf of the visitor in the internal backend (a pre-registration form); on submission it auto-passes (`scheduled`). When the visitor/guard arrives, the guard can search and find that pre-registration directly on the check-in page and check in & issue a badge, **without the visitor scanning**.
- **Mode 2 · QR-code scan registration**: the visitor scans a fixed QR code on-site and self-registers (no login); after the host (employee) reviews in the backend (toggleable) and approves, the guard checks in & issues a badge.

Both modes share the same guard check-in, blacklist, badge, long-term, and dashboard capabilities, with appointment data interoperable, so the guard can check in uniformly without distinguishing the source.

## 2. Visitor Operations

> Note: visitors participate only in **Mode 2 · QR-code scan registration**. In **Mode 1 · Pre-registration mode**, the appointment is filled by the employee on the visitor's behalf; the visitor does not need to scan, and the guard checks in directly on arrival.

**Scenario**: arriving at the enterprise, scan the fixed QR code at the guard post / factory entrance.

Steps:
1. Use WeChat or a browser to **scan the fixed universal QR code**; the appointment form opens automatically (no login).
2. Select **visitor type** (Customer / Supplier / Applicant / Delivery / Government / Tour Visitor).
3. Fill in personal info: name, phone, ID number (optional), company / organization.
4. Fill in the **host**:
   - Type the name in the "Host" field; the system matches in real time against the host list;
   - **You must select a host from the dropdown list**. If the typed name is not in the list, the system blocks submission and prompts you to contact the admin to add the host.
   > ⚠️ Key: without selecting a host from the dropdown list, the appointment cannot be submitted.
5. Fill in the visit purpose, appointment date, entry / exit time.
6. (Optional) add companions, fill in the plate number, choose whether to dine.
7. Click "Submit Appointment".
8. After submission the page shows the appointment number and result:
   - If the review toggle is **on**: shows "Please wait for the host to approve", status = pending review.
   - If the review toggle is **off**: shows "Appointment successful", status = approved, can visit directly.
9. After approval, arrive at the agreed time; the guard completes check-in.

## 3. Host (Employee) Operations

The host (employee) participates in both modes: creates pre-registrations in **Mode 1**, and reviews visitor scan submissions in **Mode 2**.

### 3.1 Mode 1: Create a Pre-registration (filled by employee)

**Scenario**: the visitor cannot scan conveniently, or the receiving party needs to register visit info in advance for arrangement reasons.

Steps:
1. Log into the backend with an employee account and go to the "**My Appointments**" page.
2. Click "**New Pre-registration**" (or go to "Appointment Management" → "New Appointment") and fill in this visit's info on the visitor's behalf:
   - Visitor name, phone, ID number (optional), company / organization;
   - Visit purpose, appointment date, entry / exit time;
   - Host defaults to the current employee (cannot be changed to someone else);
   - (Optional) companions, plate number, whether to dine.
3. Click "Submit Pre-registration".
   > Note: the pre-registration is created by the employee (`createdBy = employee`); the system **auto-approves** per existing logic, status is directly "Approved (`scheduled`)", no review wait needed.
4. After submission, view the pre-registration in "My Appointments" or "Appointment Management". When the visitor arrives, the guard searches and checks in & issues a badge directly on the check-in page.

### 3.2 Mode 2: Review Visitor Scan Appointments

**Scenario**: a visitor has submitted their own appointment via scan and it needs review.

Steps:
1. Log into the backend with an employee account and go to the "**My Appointments**" page.
2. Switch to the "**Pending Review**" tab (shown only when the review toggle is on and there are pending appointments assigned to you).
   > Note: the list shows only pending appointments where "host = current logged-in employee"; you won't see others' appointments.
3. For each appointment choose:
   - **Approve**: status becomes "Approved (`scheduled`)"; the visitor can arrive and be checked in by the guard.
   - **Reject**: reject directly; status becomes "Rejected (`rejected`)". **No reason is required when rejecting**.
   > Note: the host can only "approve / reject", and cannot modify appointment content (e.g. visit time).
4. In other tabs of "My Appointments" you can view all your related appointment records and statuses.

## 4. Guard Operations

The guard checks in & issues badges in both modes, but the appointment source differs:

- **Mode 1 (Pre-registration)**: an employee has pre-created the pre-registration in the backend (status `scheduled`). When the visitor/guard arrives, the guard can **search that pre-registration directly and check in** on the check-in page, without the visitor scanning.
- **Mode 2 (Scan appointment)**: the visitor scans and submits on-site; after host review approval the status becomes `scheduled`, then the guard searches and checks in.

### 4.1 Check-in & Check-out

Regardless of mode, the guard follows this flow:

1. Log into the backend with a guard account and go to the "**Visitor Check-in**" page.
2. In the search box enter any info: **phone / name / plate number / visitor code**, then click search.
   - The system returns matching appointments (masked, e.g. `张*`, `138****8000`).
   - If it hits the **blacklist**, the page shows a prominent red interception prompt and **check-in is not allowed**.
   - Rejected (`rejected`) appointments are excluded from search results.
   - Mode 1 pre-registrations and Mode 2 scan appointments are **presented uniformly** here; the guard doesn't need to distinguish the source.
3. After confirming identity, click "**Confirm Check-in**":
   - The system **auto-matches the badge color by visitor type** (including vehicle-pass cases, see the mapping table in 5.6), no manual selection needed.
   - Status becomes "Checked-in (`checked_in`)"; check-in time is recorded.
4. When the visitor leaves, go to the "**Visitor Check-out**" page:
   - Search on-site visitors → confirm check-out → collect the badge.
   - Status becomes "Checked-out (`checked_out`)"; check-out time is recorded.

> Key note: blacklisted visitors are auto-intercepted by the system; badge color is auto-issued by the system by visitor type — the guard just issues the badge by color.

## 5. Admin Operations

The admin has all backend permissions. Main functions:

### 5.1 Review Toggle Setting (important)
- Path: backend "**System Settings**" → Review Config.
- Toggle `review_enabled`: **on** → visitor appointments enter the host review flow; **off** → visitor submissions auto-approve.
- Default is **on (true)**, security first. It can be temporarily turned off in low-risk periods to simplify the flow; turning it on is recommended in high-risk periods.
  > Note: the toggle affects only **newly submitted** appointments; pending (`pending`) old appointments created before it was turned off are not auto-approved.
  > Note: **Mode 1 (Pre-registration)** is created by an employee in the backend (`createdBy = employee`), is not affected by the review toggle, and auto-approves on submission (`scheduled`).

### 5.2 User Management
- Path: backend "**User Management**".
- Functions: add / edit / disable users, configure roles (Admin / Guard / Employee).
- **Bulk import**: download the CSV template (fields: role, employee ID, name, department), fill it in and upload to import; the system auto-detects duplicate employee IDs and assigns a default password to new users (forced change on first login).

### 5.3 Blacklist Management
- Path: backend "**Blacklist**".
- Add to blacklist (name, ID number, phone, reason), support **permanent** or **temporary (auto-released on expiry)**.
- Blacklisted personnel are auto-intercepted at guard check-in.

### 5.4 Long-term Vehicles & Personnel Management
- Path: backend "**Long-term Vehicles / Personnel**".
- Maintain long-term vehicles and personnel: CRUD, enable / disable, validity management, on-site status view, code management.
- Long-term personnel / vehicle info is **not masked**, to help guards verify real info.

### 5.5 Host List Maintenance
- Path: backend "**Host List**" (host_contacts).
- Maintain the employee list available for visitors to match when filling forms (name, department, etc.).
- ⚠️ Important: visitors must select a host from this list to submit an appointment. Add new employees here promptly after onboarding, otherwise visitors can't book that employee.

### 5.6 Visitor Type & Badge Mapping
The system auto-matches badge color and vehicle pass by visitor type and restricts the activity area, per the following rules (implemented):

| Visitor type | Badge color | Vehicle pass | Activity area |
|----------|------------|--------|----------|
| Customer | Green | No vehicle pass | Customer parking / meeting rooms / showroom |
| Supplier | Yellow | Yellow vehicle pass | Visitor parking / meeting rooms |
| Applicant | Red | No vehicle pass | Interview room / waiting area |
| Delivery | Red | Red vehicle pass | Goods receiving / unloading area |
| Government | Yellow | Yellow vehicle pass | Visitor parking / meeting rooms |
| Tour Visitor | Yellow | No vehicle pass | Designated area |

- At guard check-in the system auto-issues the matching badge color (including vehicle-pass cases) per the table above; no manual selection needed.
- Admins can maintain the "visitor type ↔ badge color / vehicle pass / activity area" mapping in the system to ensure guards issue and guide by color and area accurately.

### 5.7 QR Code Management
- Path: backend "**QR Code Management**".
- Generate / download the fixed QR code image pointing to `/public/appointment`, printable and postable at the guard post or factory entrance.

### 5.8 Password Policy
- Path: backend "**Password Policy**".
- Configure password complexity requirements, validity period, lockout rules, etc., applied to all accounts.

### 5.9 Operation Logs
- Path: backend "**Operation Logs**".
- Records all key operations (operator, type, module, description, time, IP), with multi-dimensional filtering for audit tracing.

### 5.10 Visitor Dashboard
- Path: backend "**Visitor Dashboard**".
- Stat cards (total appointments / check-ins / on-site, etc.) + charts (visit-purpose distribution / type distribution / trends), with time-range and host filtering.

### 5.11 Appointment Management
- Path: backend "**Appointment Management**".
- Query (filter by time / status / visitor type, etc.), view details, modify appointments, export (CSV / Excel).

## 6. General Notes & FAQ

- **Two registration modes coexist**: visitors can scan a fixed QR code to self-register (guard checks in after host approval), or a host employee can pre-enter a "pre-registration" on the internal PC (no review, guard checks in directly on the pre-registration); both paths share the guard check-in / badge issuance / check-out and blacklist logic.
- **Visitors don't need to log in**: visitors complete appointments entirely by scanning and filling forms, without using a backend account; in pre-registration mode visitors need no action either.
- **Host must be selected**: without selecting a host from the dropdown list, submission is blocked.
- **Review toggle affects new appointments**: after turning off, new submissions auto-approve; existing `pending` old appointments are unaffected.
- **No reason required for rejection**: the host can reject directly; the system doesn't force a reason.
- **Blacklist auto-interception**: hitting the blacklist at guard check-in blocks entry, cannot be bypassed.
- **Data masking**: names, phones, and IDs are masked in lists and details (e.g. `张*`, `138****8000`); long-term vehicles / personnel are not masked.
- **Change default passwords promptly**: password change is forced on first login; in production immediately change all default passwords for admin / security / employee / visitor.
