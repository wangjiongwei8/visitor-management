# Visitor Management System (Open Source) — Deployment Guide

> Audience: those who want to deploy and operate this system themselves (ops / admin / developer).
> This document is used together with the Operations Manual. The system is based on Next.js 16 + TypeScript + Tailwind CSS + Drizzle ORM + PostgreSQL, MIT License.
> The system has zero external dependencies: it runs without configuring email or SMS gateways.

## 1. Environment Requirements

| Component | Version | Notes |
|------|----------|------|
| Node.js | 20+ | Only needed for local dev / build; the Docker image is based on `node:20-alpine` and provides the runtime inside the image, host doesn't need it installed |
| PostgreSQL | 16 | Database (Docker mode bundles `postgres:16-alpine`) |
| pnpm | 9+ | Package manager |
| Docker / Docker Compose | Latest stable | Only needed for Option 1 (Docker deploy) |
| OS | Linux / macOS / Windows | — |

## 2. Option 1: Docker One-Command Deploy (Recommended)

1. Copy the env template:
   ```bash
   cp .env.example .env
   ```
2. Edit `.env`, setting at least `DATABASE_URL` and `TOKEN_SECRET` (see Section 5). For Docker deploy, `DATABASE_URL` can usually keep the template default, but `TOKEN_SECRET` **must be changed to a long random string**.
3. Start the services:
   ```bash
   docker compose up -d
   ```
   This starts two containers: PostgreSQL (`visitor_db`, port 5432) and the app (`visitor_app`, port 4000). On startup the app container **auto-syncs the DB schema** and **creates default accounts** — no manual initialization needed.
4. Open `http://localhost:4000` in a browser and log in with the default accounts (see Section 6); password change is forced on first login.

> Built-in container health check: the app probes `http://localhost:4000/api/health` every 30s; the app starts only after the database is ready. The schema is created by the app auto-running `drizzle-kit push` at startup.

## 3. Option 2: Local Development

```bash
pnpm install
cp .env.example .env.local      # Fill in DATABASE_URL and TOKEN_SECRET
pnpm db:push                    # First deploy: sync schema to DB (app also auto-creates tables at startup)
pnpm dev                        # Start dev server, visit http://localhost:3001
```

Other common commands:
```bash
pnpm test        # Run Vitest test suite (27 core tests)
pnpm build       # Production build (see Section 8)
pnpm start       # Run the build in production mode
```

> Local development requires you to provide your own PostgreSQL 16 instance (Node.js 20+) and point `DATABASE_URL` to it correctly.

| Item | Docker deploy | Local dev |
|----|-------------|----------|
| Access URL | http://localhost:4000 | http://localhost:3001 |
| Database | Auto-started inside container | Must provide your own |

## 5. Full Environment Variable Reference

All variables are in the repo-root `.env.example`. For **Docker deploy** copy to `.env` (`docker compose` reads `.env` by default, not `.env.local` / `.env.production`); for **local dev** copy to `.env.local` (auto-loaded by Next.js).

| Variable | Required | Default / example | Description | Risk |
|--------|------|---------------|------|------|
| `DATABASE_URL` | ✅ Required | `postgresql://postgres:password@localhost:5432/visitor_management` | PostgreSQL connection string, format `postgresql://<user>:<password>@<host>:<port>/<db>` | Contains DB password; never use the example weak password in production; Docker mode points to in-container `db:5432` by default, usually no change needed |
| `TOKEN_SECRET` | ✅ Required | `replace-with-a-long-random-string-at-least-32-chars` | HMAC-SHA256 signing secret for login tokens | **High risk**: must be overridden with a long random string in production; default or weak key allows token forgery → privilege escalation. Generate: `openssl rand -hex 32` |
| `NODE_ENV` | ✅ Required | `production` | Runtime env: `development` or `production` | Must be `production` in prod; `development` exposes error stacks and debug info |
| `DB_PASSWORD` | ⚠️ Docker only | `password` | Used only when `docker compose` initializes the database; written to both the PostgreSQL container and `DATABASE_URL` | Must be changed to a strong password in production; default is very weak |
| `DOCKER_USERNAME` | Optional | `your-dockerhub-username` | Username for pushing images to Docker Hub | No security impact |
| `VERSION` | Optional | `latest` | Version tag for the built image | No security impact |

> 🔒 The source code contains **no** customer-specific secrets. All secrets exist only in local `.env` (Docker deploy) or `.env.local` (local dev), all ignored by `.gitignore` (including `.env` itself), and never enter the repo.

## 6. Database & Initialization

- Database name: `visitor_management`. Auto-created by the `postgres:16-alpine` container in Docker deploy.
- Review toggle: the `review_enabled` key in the `system_settings` table, default `"true"` (i.e. review on by default, security first).
- After first access, complete initialization; the admin can set password policy, host list, etc.

**Default accounts (password change forced on first login)**:

| Role | Username | Initial password | Notes |
|------|--------|----------|------|
| Admin | `admin` | `admin123` | Full backend permissions |
| Guard | `security` | `security123` | Visitor check-in / check-out |
| Employee | `employee` | `employee123` | Host review, my appointments |
| Visitor | `visitor` | `visitor123` | Appointment query / demo |

> ⚠️ After deploying to production, immediately change all the default passwords above. Visitors don't need to log in to scan and book, and don't need the `visitor` account.

## 7. Health Check

The system provides a health-check endpoint:
```
GET /api/health
```
Returns HTTP 200 when the app and database are connected normally. Can be used for load-balancer liveness or container health checks (enabled by default in Docker deploy).

## 8. Production Build

Production build command:
```bash
pnpm build
```
This is equivalent to `next build --webpack`.

> ⚠️ **You must build with webpack; Turbopack is forbidden.** `Turbopack` is incompatible with `bcryptjs`; building or running with Turbopack breaks the auth module. The Dockerfile already runs `pnpm run build` (`next build --webpack`).

After the build, it runs in standalone mode, listening on `0.0.0.0:4000`.

## 9. Data Backup & Version Upgrade

### Data Backup
All business data is stored in the PostgreSQL `visitor_management` database, persisted via the `postgres_data` volume. Regular backups are recommended:
```bash
# Docker mode
docker exec visitor_db pg_dump -U postgres visitor_management > backup_$(date +%F).sql

# Or local psql client
pg_dump -h localhost -U postgres visitor_management > backup_$(date +%F).sql
```
Restore:
```bash
psql -h localhost -U postgres -d visitor_management < backup_YYYY-MM-DD.sql
```

### Version Upgrade
This system maintains **zero database schema changes**; upgrades mostly replace app code / image:
1. Always take a full backup before upgrading (see above).
2. Read the target version's Release Notes and confirm no new migration scripts.
3. Docker mode:
   ```bash
   git pull                 # or pull a new image
   docker compose pull
   docker compose up -d
   ```
   The `postgres_data` volume is not destroyed with the container, so upgrades don't lose data.
4. Local mode: pull new code → `pnpm install` → `pnpm build` → restart service.

> After upgrading, it's recommended to hit `/api/health` to confirm health, and log in with the default admin account to verify key functions.

## 10. Optional: Nginx Reverse Proxy

You can place Nginx as a reverse proxy in front of the app (e.g. to expose 80/443 and unify TLS termination). The following is a **generic example config** (placeholder domain `example.com`, app running at `127.0.0.1:4000`) for reference only:

```nginx
# Example only, using placeholder domain example.com; do not write real domain / IP
server {
    listen 80;
    server_name example.com;

    # If uploading QR images etc., you may raise the body size limit
    client_max_body_size 10m;

    location / {
        proxy_pass http://127.0.0.1:4000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # If WebSocket realtime is enabled later, keep these two lines
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";

        proxy_read_timeout 60s;
    }
}
```

**Next.js reverse-proxy notes**:
- The app runs in standalone mode on the container / process `4000` port; point `proxy_pass` there.
- If serving HTTPS externally, configure TLS in Nginx and set `X-Forwarded-Proto` to `https`, otherwise the app may misjudge the access protocol and generate wrong absolute links.
- To get the real client IP at the app layer (rate limiting, operation-log IP recording), ensure `X-Forwarded-For` is passed through; the app's own auth and logic don't depend on proxy headers, so security is unaffected.
- When enabling WebSocket, keep the `Upgrade` / `Connection` headers, otherwise the connection will be dropped.
- The repo root **no longer contains a physical `nginx.conf` file**; this section is an in-doc reference example — maintain the proxy config yourself as needed.
