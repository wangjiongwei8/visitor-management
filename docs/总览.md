# 访客管理系统（开源版）— 设计总览

> 本文档是**入口说明**，配合 `PRD-访客管理系统.md`（需求）与 `ARCHITECTURE.md`（架构）使用。
> 本系统为独立开源项目（MIT 协议），任何组织可自行部署使用。

---

## 一、系统说明

本系统将「员工在客户内网帮访客创建预约」的模式，升级为「**访客扫固定二维码自助填表**」，并把「管理员统一审批」改为「**被访人本人审核（可开关）**」。所有已有功能（黑名单、长约车辆、用户管理、操作日志、访客看板等）完整保留。

设计原则：**最小变更**——本系统不是重写，而是在现有代码基础上的增量改造；数据库零表结构变更、零新增 npm 依赖。

## 二、核心特性

| 维度 | 说明 |
|------|------|
| 预约发起方 | **访客扫固定二维码自助填表**（无需登录） |
| 审批人 | **被访人（员工）本人审核** |
| 审核机制 | **可开关**：开启→被访人审核；关闭→自动通过 |
| 出差/外勤支持 | 访客/员工均可公网访问，无网络限制 |
| 邮件/短信通知 | **已移除**（纯系统内操作） |
| 访客证打印 | **已移除** |
| 开源 | **是（MIT）** |

## 三、核心业务流程

系统支持两种并行的登记模式，门卫签到流程共用：

- **模式一 · 电脑端内部审核（预审单模式）**：员工在内部后台代为填写来访预约（预审单），提交后自动通过（`scheduled`）；访客 / 门卫到现场时，门卫可直接在该预审单上签到发牌，无需扫码。
- **模式二 · 二维码扫码登记模式**：访客到现场扫描固定二维码自助填表（无需登录），被访人（员工）后台审核（可开关）通过后，门卫签到。

```
访客扫固定二维码（贴在门卫处）
   │
   ▼
填写预约表单（受访人需从清单下拉选定，硬阻止无效提交）
   │
   ├─ 审核开关=关闭 ──────────────► status = scheduled（自动通过）
   │
   └─ 审核开关=开启 ──► status = pending
                              │
                              ▼
                       被访人（员工）登录后台审核
                              │
                    ┌─────────┴─────────┐
                通过 │                   │ 拒绝（无需原因）
                    ▼                   ▼
            status=scheduled      status=rejected
                    │
                    ▼
            门卫搜索（手机号/姓名/车牌/访客编号）→ 黑名单自动拦截 → 签到发牌 → 签退
```

### 模式一（预审单）流程

```
员工在内部后台填写预审单（受访人=本人）
   │
   ▼
提交 → 系统按现有逻辑自动通过（createdBy=employee）
   │
   ▼
status = scheduled（无需审核）
   │
   ▼
门卫搜索（手机号/姓名/车牌/访客编号）→ 直接命中预审单 → 黑名单自动拦截 → 签到发牌 → 签退
```

> 说明：模式一由员工创建，不触发被访人审核，也不要求访客扫码；门卫到现场即可直接签到。

状态枚举：`pending → scheduled → checked_in → checked_out`，拒绝为 `rejected`（签到搜索排除 `rejected`）。

## 四、已确认的产品决策（Q1–Q7 锁定）

| 编号 | 决策点 | 结论 |
|------|--------|------|
| Q1 | 审核是否区分访客类型 | 否，单一全局开关 |
| Q2 | 受访人不在 `host_contacts` 清单 | **硬阻止提交**（必须下拉选定受访人才放行） |
| Q3 | 被访人审核时能否修改预约 | 否，仅通过 / 拒绝 |
| Q4 | 关闭审核后已有 pending 是否批量转 | 否，仅影响新提交 |
| Q5 | 门卫签到搜索是否排除 rejected | 是 |
| Q6 | 拒绝是否需填原因 | **否，直接拒绝** |
| Q7 | 公开预约页是否加验证码 | 否（已有 IP 级速率限制） |
| — | 审核开关默认值 | `true`（开启审核，安全优先） |
| — | 通知方式 | 不需要邮件 / 短信 |

## 五、技术架构要点

- **技术栈**：Next.js 16 (App Router) + TypeScript + Tailwind CSS + shadcn/ui + Drizzle ORM + PostgreSQL
- **数据库**：**零表结构变更**。审核开关仅用 `system_settings` 表的 `review_enabled` 键（默认 `"true"`）
- **新增 npm 包**：无；**移除** `nodemailer` / `@aws-sdk/client-s3` 等废弃依赖
- **新增文件**：
  - `src/app/api/settings/public/route.ts` — 免认证返回审核开关状态
  - `src/components/visitor/host-contact-search.tsx` — 受访人下拉匹配（硬阻止无效提交）
  - `src/lib/review-status.ts` — 审核状态纯函数（测试用）
  - `tests/` — Vitest 测试套件
- **审核分流**：`scan-appointment` 提交时查 `review_enabled` → `true` 置 `pending`，`false` 置 `scheduled`；`createdBy` 均为 `visitor`
- **被访人匹配**：复用已有 `/api/host-contacts?query=`，前端下拉选定才算有效

## 七、开源与部署

### 环境变量（见 `.env.example`）
- `DATABASE_URL` — PostgreSQL 连接串（必填）
- `TOKEN_SECRET` — Token 签名密钥（**必填，生产必须覆盖，不可用默认值**）
- `NODE_ENV` — `development` / `production`

> ⚠️ 源码中**不含**任何客户专属密钥（IP / 数据库密码 / Token）。密钥仅存在于 `.env.local` / `.env.production`，已被 `.gitignore` 忽略，不会进入仓库。

### 一键部署
```bash
cp .env.example .env.local   # 填入 DATABASE_URL / TOKEN_SECRET
docker compose up -d         # 自动拉起 PostgreSQL + 应用
# 首次访问 http://localhost:4000 完成初始化（管理员密码等）
```

### 本地开发
```bash
pnpm install
pnpm dev                     # http://localhost:3001
pnpm test                    # 运行 Vitest
```
