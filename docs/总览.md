# Visitor Management System (Open Source) — Design Overview

> This document is the **entry point**, used together with `PRD-访客管理系统.md` (requirements) and `ARCHITECTURE.md` (architecture).
> This system is an independent open-source project (MIT License); any organization may deploy and use it.

---

## 1. System Overview

This system upgrades the "employee creates appointments for visitors inside the customer's intranet" model into "**visitors scan a fixed QR code and self-register**", and changes "admin unified approval" into "**host (employee) reviews in person (toggleable)**". All existing features (blacklist, long-term vehicles, user management, operation logs, visitor dashboard, etc.) are fully retained.

Design principle: **minimal change** — this is not a rewrite but an incremental enhancement on top of the existing code; zero database schema changes, zero new npm dependencies.

| Dimension | Description |

| Approver | **Host (employee) reviews in person** |
| Review mechanism | **Toggleable**: on → host reviews; off → auto-approve |
| Travel / field support | Visitors/employees can both access over the public internet, no network restrictions |
| Email/SMS notifications | **Removed** (in-app operations only) |
| Visitor badge printing | **Removed** |
| Open source | **Yes (MIT)** |

## 3. Core Business Flow

The system supports two parallel registration modes, sharing the guard check-in flow:

- **Mode 1 · Internal backend review (Pre-registration mode)**: an employee fills in the visit appointment on behalf of the visitor in the internal backend (a pre-registration form). On submission it auto-passes (`scheduled`); when the visitor/guard arrives, the guard can check in and issue a badge directly from that pre-registration form without scanning.
- **Mode 2 · QR-code scan registration**: the visitor scans a fixed QR code on-site and self-registers (no login); after the host (employee) reviews in the backend (toggleable) and approves, the guard checks in.

```
Visitor scans fixed QR code (posted at the guard post)
   │
   ▼
Fill appointment form (host must be selected from the dropdown list; invalid submissions are hard-blocked)
   │
   ├─ Review toggle = off ──────────────► status = scheduled (auto-approve)
   │
   └─ Review toggle = on ──► status = pending
                              │
                              ▼
                       Host (employee) logs into backend to review
                              │
                    ┌─────────┴─────────┐
                Approve │                │ Reject (no reason required)
                       ▼                ▼
               status=scheduled      status=rejected
                       │
                       ▼
     Guard searches (phone/name/plate/visitor code) → auto blacklist interception → check in & issue badge → check out
```

### Mode 1 (Pre-registration) Flow

```
Employee fills pre-registration form in internal backend (host = self)
   │
   ▼
Submit → system auto-approves per existing logic (createdBy=employee)
   │
   ▼
status = scheduled (no review needed)
   │
   ▼
Guard searches (phone/name/plate/visitor code) → directly matches pre-registration → auto blacklist interception → check in & issue badge → check out
```

> Note: Mode 1 is created by an employee, does not trigger host review, and does not require the visitor to scan; the guard can check in directly on arrival.

Status enum: `pending → scheduled → checked_in → checked_out`; rejection is `rejected` (excluded from check-in search).

## 4. Confirmed Product Decisions (Q1–Q7 locked)

| ID | Decision point | Conclusion |
|------|--------|------|
| Q1 | Does review distinguish visitor types | No, single global toggle |
| Q2 | Host not in `host_contacts` list | **Hard-block submission** (must select a host from the dropdown to proceed) |
| Q3 | Can host modify the appointment during review | No, approve / reject only |
| Q4 | When review is turned off, bulk-convert existing pending | No, affects new submissions only |
| Q5 | Should guard check-in search exclude rejected | Yes |
| Q6 | Is a reason required for rejection | **No, reject directly** |
| Q7 | Add CAPTCHA to the public appointment page | No (IP-level rate limiting already in place) |
| — | Review toggle default | `true` (review on, security first) |
| — | Notification method | No email / SMS needed |

## 5. Technical Architecture Highlights

- **Tech stack**: Next.js 16 (App Router) + TypeScript + Tailwind CSS + shadcn/ui + Drizzle ORM + PostgreSQL
- **Database**: **zero schema changes**. The review toggle uses only the `review_enabled` key in the `system_settings` table (default `"true"`)
- **New npm packages**: none; **removed** deprecated deps like `nodemailer` / `@aws-sdk/client-s3`
- **New files**:
  - `src/app/api/settings/public/route.ts` — returns review toggle status without auth
  - `src/components/visitor/host-contact-search.tsx` — host dropdown matching (hard-blocks invalid submissions)
  - `src/lib/review-status.ts` — review status pure functions (for testing)
  - `tests/` — Vitest test suite
- **Review branching**: on `scan-appointment` submit, read `review_enabled` → `true` sets `pending`, `false` sets `scheduled`; `createdBy` is always `visitor`
- **Host matching**: reuse existing `/api/host-contacts?query=`, valid only when selected from the frontend dropdown

## 7. Open Source & Deployment

### Environment Variables (see `.env.example`)
- `DATABASE_URL` — PostgreSQL connection string (required)
- `TOKEN_SECRET` — Token signing secret (**required, must be overridden in production, never use the default**)
- `NODE_ENV` — `development` / `production`

> ⚠️ The source code contains **no** customer-specific secrets (IP / DB password / Token). Secrets exist only in `.env.local` / `.env.production`, ignored by `.gitignore`, and never enter the repo.

### One-Command Deploy
```bash
cp .env.example .env.local   # Fill in DATABASE_URL / TOKEN_SECRET
docker compose up -d         # Auto-starts PostgreSQL + app
# First visit http://localhost:4000 to complete initialization (admin password, etc.)
```

### Local Development
```bash
pnpm install
pnpm dev                     # http://localhost:3001
pnpm test                    # Run Vitest
```
